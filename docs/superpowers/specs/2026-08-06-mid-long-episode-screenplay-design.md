# 中长剧分集与剧本分层设计

## 已确认的产品决定

- 默认产品是“单集完整中长剧”，而不是把一章自动压成多个竖屏短集。
- 旧项目、旧 `NovelPromotionClip` 数据和旧 API 合约不需要兼容或迁移。
- 本次改造的唯一目标是让读者先获得完整、连续、可审阅的本集剧本；视频模型的细粒度执行需要不能反向决定剧本结构。
- 旧数据不在本次代码改动中自动删除。若要清空旧开发数据库，必须由用户单独确认执行目标和范围。

## 问题

当前流程有两个互相独立的切分层：

1. 智能分集把原文分析成叙事场景，再按剧集目标、冲突、结果和钩子安排分集。
2. 故事转剧本再次按“内容元素”切成 `clip`，并独立生成每个 clip 的剧本。

第二层的 `clip` 是为下游模型调用准备的容器，却同时承载了剧本的主要阅读体验。因此一段完整的中长剧会被显示成多份零散小剧本，短尾片段也没有足够的叙事价值。

## 产品原则

- **分集不等于场景，场景不等于镜头，镜头不等于视频执行段。** UI、数据和 API 都必须保留这四层名称与关系。
- 分集边界由完整戏剧运动决定：主角目标、阻力、选择、结果、悬念、关键时空切换。时长只用于提示异常，绝不硬切。
- 剧本场景是唯一的可读、可编辑叙事单元。每个场景具有连续时空、入口状态、目标、冲突、结果和出口状态。
- 视频执行段只是模型能力、重试、计费和连续性控制的容器。它不能成为剧本页面的一级项目。
- 任何自动拆分都必须精确覆盖来源：顺序不变、无遗漏、无重叠。

## 目标用户体验

以《青山1》为代表的约 11 分钟文本：

1. 智能分集得到一个完整分集，附分集卡：主线、集内目标、升级、集尾钩子。
2. “剧本”页显示一份连续剧本，内部可展开约四个自然场景，例如问诊、走廊交易、六楼病房、李青鸟线索。
3. 用户在“制作分镜”页才会看到每个场景拆出的镜头和视频执行段。
4. 一个 15 秒视频段可以容纳同一连续时间线上的多个镜头；视频段短小不改变剧本场景数量。

## 目标架构

```text
原始故事
  -> 语义分集
  -> EpisodeCard（本集目标、结构、钩子）
  -> EpisodeScreenplay（本集唯一剧本）
  -> ScreenplayScene（可读、可编辑的场景）
  -> ShotPlan（镜头规划）
  -> ProductionSegment（视频模型执行段）
```

### 1. 语义分集

保留现有“源单元 -> 叙事场景 -> 全局分集计划 -> 精确覆盖校验”的设计，但把默认 profile 改为中长剧 profile：

- 目标单集时长 8–15 分钟；时长仅作软约束。
- 不自动选择横版短集 profile，也不接受固定字数或固定元素数作为集边界。
- 分集结果必须持久化 `EpisodeCard` 所需元数据：主线、核心目标、戏剧弧线、集尾钩子、场景范围。

### 2. 本集剧本生成

“故事转剧本”接收完整 `NovelPromotionEpisode` 和已确认的 EpisodeCard，而不是先创建 clip。

生成步骤：

1. 对整集做一次人物、地点、道具和关系状态分析，建立本集连续性上下文。
2. 生成 `ScreenplayScenePlan[]`：每项给出来源范围、场景头、入口状态、目标、冲突、结果、出口状态、参与角色和关键资产。
3. 对每个完整场景生成标准剧本文本。大集可按场景并发调用模型，但模型输入必须包含 EpisodeCard、前一场出口状态和统一资产库。
4. 本地合并为唯一的 EpisodeScreenplay，并验证场景顺序、来源覆盖、连续性字段和剧本结构。

剧本提示词不得再包含“20 个内容元素”“新角色即切分”“按模型批次切分”等规则。连续动作、完整对白往返和同一情绪过程必须保留在同一场景中。

### 3. 制作分镜与视频执行段

剧本确认后，单独发起“制作分镜”任务：

- `ShotPlan` 关联一个 `ScreenplayScene`，记录镜头目的、时间线位置、主体、动作、对白、入点和出点。
- `ProductionSegment` 关联一个或多个连续 ShotPlan，记录模型、允许时长、最终提示词、参考资产、入口/出口视觉状态和任务状态。
- 分段以允许的最长视频时长和最少段数为优先；只有尾部余量或模型硬上限允许产生较短段。
- 同一场景中连续的动作、对白和镜头可被装入同一执行段。未完成动作不得跨独立段。

### 4. 数据模型

旧 `NovelPromotionClip` 不再承担剧本含义。新模型按职责命名：

- `NovelPromotionEpisodeCard`：一对一关联 episode，保存分集级叙事元数据和源场景范围。
- `NovelPromotionScreenplay`：一对一关联 episode，保存剧本版本、源文本指纹、结构化剧本和纯文本导出。
- `NovelPromotionScreenplayScene`：多对一关联 screenplay，保存顺序、来源范围、场景头、入口/出口状态、叙事元数据和标准剧本块。
- `NovelPromotionShotPlan`：多对一关联 screenplay scene，保存时间线和镜头设计。
- `NovelPromotionProductionSegment`：多对多或有序一对多关联 ShotPlan，保存视频生成执行信息。

现有 `NovelPromotionClip`、以它为输入的 screenplay API、以及依赖其字段的 UI/worker 在一次不兼容改造中移除或改写；不得保留双写、旧字段 fallback 或旧项目分支。

## UI 设计

工作区固定为三个阶段：

- **剧本**：显示 EpisodeCard 和连续 EpisodeScreenplay。侧栏仅列 ScreenplayScene；默认显示完整剧本，场景可折叠但不拆成独立文档。
- **制作分镜**：显示一个场景下的镜头规划；用户可看每个镜头如何覆盖剧本动作和对白。
- **视频制作**：显示 ProductionSegment、素材、任务进度、失败重试和输出。它不显示为“剧本片段”。

每个层级都显示自己的计数和名称，禁止用“片段”混称场景、镜头和视频执行段。

## 完整性与错误处理

- 场景计划若存在来源空洞、重叠、乱序、无场景头、缺失入口/出口状态，拒绝生成并将精确校验错误返回给规划模型进行一次修复。
- 某个场景的剧本生成失败时，整个本集剧本标为未完成；成功场景可保留为草稿，但不能被下游制作分镜读取。
- 生产分镜失败不影响已确认的剧本。失败段只能重试该 ProductionSegment，不重新切分或重写本集剧本。
- 短尾段规则属于 ProductionSegment 阶段：除非它是明确的场景/集尾落点，否则合并到前段；该规则绝不删除或合并剧本场景。

## 非目标

- 不迁移、修复或保留旧项目。
- 不自动删除数据库中的旧项目数据。
- 不改变视频模型本身的时长能力。
- 不以镜头数量、画幅或风格标签反向扩写剧情。

## 验收标准

- 《青山1》可生成一个完整中长剧分集和一份连续剧本；剧本阅读层不存在 clip 列表。
- 每个 ScreenplayScene 都有场景头、来源范围、目标、冲突、结果、入口状态和出口状态。
- 整集来源文本被场景精确覆盖一次，且场景合并后与来源一致。
- 新角色、一句对白、单个反应、视频模型的时长限制都不能单独触发剧本场景切分。
- ProductionSegment 仅在“视频制作”阶段出现，且每个段可追溯到其 ShotPlan 和 ScreenplayScene。
- 单个 ProductionSegment 重试不会改变剧本、场景或其他已完成段。
- 单元、worker、API 合约和页面测试均以新模型为唯一合约，不包含旧 `Clip` fallback 测试。

## 实施顺序

1. 先建立新的 screenplay/scene 数据模型和剧本生成任务，替换故事转剧本路径。
2. 再将剧本页面切换到新的 EpisodeScreenplay/ScreenplayScene 数据。
3. 把现有分镜规划改为从 ScreenplayScene 读取，而非从 clip 读取。
4. 最后建立 ProductionSegment，并把视频任务、重试和状态移到该层。
5. 仅在全部新链路通过后，删除旧 clip 相关 API、worker、组件和测试。
